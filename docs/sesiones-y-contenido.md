# Sesiones y contenido importado

La bóveda y la cuenta de usuario son sesiones independientes. El token de bóveda actual se conserva en `localStorage`; el de usuario en `sessionStorage`. Ambos son accesibles a JavaScript del mismo origen. Los permisos de usuario y de bóveda se comprueban por separado en el servidor. No se debe interpretar que desbloquear la bóveda inicia sesión en la cuenta.

El bloqueo envía `/auth/lock` para revocar la sesión de bóveda y elimina el token local aun si la petición falla. En caso de fallo, la interfaz indica que la revocación del servidor no pudo confirmarse; el token remoto permanece sujeto a su expiración y revocación de servidor. El cierre de cuenta tiene un ciclo independiente.

Los informes Markdown se saneaan con DOMPurify antes de renderizar HTML; Mermaid usa modo estricto y saneamiento SVG. Los fragmentos HTML se ejecutan en un iframe sin permisos de sandbox. Estas defensas no constituyen una garantía general contra XSS: cualquier nueva ruta de HTML importado debe revisarse junto con su política de recursos y pruebas de regresión.

Una migración a cookies `HttpOnly` y `Secure` reduciría el acceso directo de JavaScript a los tokens, pero requiere cambiar emisión, autenticación de todas las rutas y pasarela C2, protección CSRF en operaciones mutables, políticas `SameSite` y manejo de HTTPS/proxy, expiración, bloqueo y cierre en múltiples pestañas. Antes de activarla se requieren pruebas de compatibilidad y revocación con un entorno desechable; cambiar solo el almacenamiento del navegador rompería las sesiones existentes. No se introdujo un cambio parcial del contrato de autenticación.

## Reserva y bloqueo de writeups

La pestaña conserva los identificadores del último informe y pizarra, y el modo de vista. Las copias de trabajo se almacenan cifradas aparte. Si una recarga conserva la sesión de bóveda pero borra la clave local de la memoria, **Revisar copia local** permite verificar la contraseña y derivar de nuevo esa clave sin sustituir el token de bóveda.

Las mutaciones de un writeup existente requieren una reserva de edición activa. El cliente obtiene una con `POST /api/v1/writeups/{id}/edit-lease`, enviando `client_id` (16–128 caracteres). La respuesta incluye un token efímero de reserva, válido por 90 segundos. En cada mutación del informe, sus pizarras, citas o evidencias, el cliente envía ese valor en `X-Writeup-Edit-Lease` y el mismo `client_id` en `X-Writeup-Client-ID`. La reserva se renueva con el mismo `POST` y se libera con `DELETE /api/v1/writeups/{id}/edit-lease`.

Una reserva ausente, vencida o perteneciente a otra sesión devuelve HTTP `423`; el cliente debe volver a adquirirla antes de reintentar. Renovar una reserva activa exige el mismo token y `client_id`. El bloqueo manual se gestiona con `POST` y `DELETE /api/v1/writeups/{id}/manual-lock`; si la solicitud incluye una cuenta, puede retirarlo esa misma cuenta o una persona propietaria. En modo solo bóveda no existe un identificador duradero cuando el token rota, por lo que cualquier sesión de bóveda válida puede retirar el bloqueo. Las rutas de lectura, vista previa, exportación y clonación no requieren reserva. Crear un writeup nuevo con `POST /api/v1/writeups` tampoco la requiere. El cierre normal de la bóveda intenta liberar la reserva primero; un cierre abrupto deja que venza automáticamente en un máximo de 90 segundos. Los clientes API existentes que muten informes deben incorporar el ciclo de reserva antes de actualizarse.
